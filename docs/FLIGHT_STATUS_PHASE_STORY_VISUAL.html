Uçuş hikâyesi — fazlar, cron API, statü önceliği

Örnek: PDF’den PC000 içe aktarıldı, planlı kalkış 17:00 (aynı gün). Sabah 09:00’da import. Aşağıdaki saatler hikâye için yerel eksen; veritabanında scheduled_departure UTC timestamptz olarak tutulur. Faz hesabı: compute_flight_api_phase_state (migration 20260330120000_pdf_spec_api_refresh_phase.sql).

09:00 — PDF import anı

Uçuş satırı oluşur: scheduled_departure = 17:00 (roster günü), scheduled_arrival ör. 19:00. İlk kayıtta estimated_* ve delay_dep_min genelde boş → ETD = STD.

Şu an: now = 09:00 < STD − 3 saat = 14:00 → faz passive_future

Cron job check-flight-status-and-notify bu satırı listeye almaz (yalnızca semi_active ve active). Harici API tüketimi yok.

Pilot rostere girerse mobil uygulama kendi akışıyla (Edge / flightApi) arama yapabilir; bu, cron’dan bağımsızdır.

Faz geçişleri (ETD = coalesce(estimated_departure, STD + delay_dep))
FazKoşul (özet)Cron’da API?
passive_futurenow < STD − 3hHayır
semi_activeSTD − 3h ≤ now < ETD − 30dkEvet — plan / tahmin güncelle
activenow ≥ ETD − 30dk (veya phase_active_locked)Evet — statü + FR24 + bildirim
passive_pastİniş sinyalleri veya stale pencere (PDF spec)Cron bu satırı listelemez; pasif bakım ayrı

PDF import sonrası gecikme güncellenince estimated_departure veya delay_dep_min değişir → ETD kayar; semi_active penceresi buna göre uzayıp kısalabilir. Bir kez active + kilit ile faz, dalgalanmada geri düşmeyi zorlaştırır (phase_active_locked).

Gün boyu zaman çizelgesi — PC000

Varsayım: gecikme yok, ETD = 17:00 → aktif faz 16:30’da başlar.

09:00 — PDF import
passive_future · flight_status tipik: scheduled. Cron bu uçuş için dış API çağırmaz.
14:00 — STD − 3 saat
semi_active başlar. Cron her çalıştığında bu satır işlenir.
API (semi_active): Önce roster poll önbelleği varsa onu uygula. Yoksa fetchTimetablePrimary → sırayla AirLabs /flight, gerekirse AeroDataBox; belirsizlikte AeroAPI / Aviationstack. Plan zayıfsa FR24 light (flight-summary/light) ile estimated_* ve fr24_progress_* doldurulabilir. Sonuç: estimated_departure, estimated_arrival, gecikme alanları, airlabs_progress_percent.
16:30 — ETD − 30 dakika
active + phase_active_locked = true. Statü ve aile bildirimleri bu fazda devreye girer (bildirimler yalnız active iken).
API (active, her cron turu): Önce yine fetchTimetablePrimary ile AirLabs (+ yedekler) → estimated_* ve gecikme DB’ye yazılır. Ardından aşağıdaki statü öncelik merdiveni (çoğunlukla FR24 selectFr24Flight + deriveFr24LiveStatus).
16:30 … 19:xx — Uçuş yaşanıyor
FR24: first_seen → taxi_out, datetime_takeoff → en_route, datetime_landed → landed. last_seen tek başına iniş kanıtı değildir. AirLabs iptal/aktarmada üst sıralarda keser.
İniş sonrası
passive_past (iniş sinyali veya stale kural). Cron ana liste dışı kalır; uçuş “hikâyesi” veritabanında tamamlanmış sayılır.
Active faz — statü belirleme önceliği (check-flight-status-and-notify)

Aynı turda önce timetable metadata çekilir; status kararında active faz için FR24 birinci kaynak, diğerleri fallback'tir.

  1. FR24 (birinci kaynak) → deriveFr24LiveStatus (first_seen, datetime_takeoff, datetime_landed, last_seen) → scheduled / taxi_out / en_route / landed. Aynı turda fr24ProgressBarPatch ile çubuk alanları güncellenebilir.
  2. FR24 yok / sonuç yoksa fallback → AirLabs iptal/divert önceliği, ardından actualIn (landed), actualOut+scheduled (en_route) ve mapAirLabsStatus (landed metni tek başına kesin değil).

Hard guard (DV2): landed yazımı / landed push yalnızca güçlü kanıtla yapılır: fr24.datetime_landed veya güvenilir actual_in/actual_arrival. last_seen ya da çıplak AirLabs landed metni tek başına iniş sayılmaz.
